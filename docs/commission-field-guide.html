The big picture

One employee, one plan, one month. Everything else is detail.

A commission is never attached to an employee directly. It falls out of four things meeting: an employee whose role is inside a plan's scope, the employee's transactions for one period, and the plan's KPIs with their pay-rate slabs. The engine walks that chain for every employee in scope and writes one payout row per person.

Two ideas carry most of the weight. First, a KPI in a plan is either a payout KPI with a weight above zero and a slab, or a monitor KPI with weight exactly zero and deduction bands. Payout KPIs add money; monitor KPIs can only take a percentage away. Second, the formula output is compared to the slab directly. The engine does not divide by target any more, so a ratio KPI must already produce a percentage.

Employees and scope

How a person becomes eligible for a plan, and whose transactions count as theirs.

An employee row carries four fields the engine cares about: role_uid, sales_office_uid, reports_to_uid and is_active. The plan side carries three lists. The engine intersects them in this order.

  1. Role gate. Every active employee whose role is in plan_roles. If the plan has no roles, nobody qualifies. This is why the two ASM plans currently produce zero employees.
  2. Office gate. If plan_sales_offices is non-empty, keep only employees in one of those offices. The builder does not expose this list, so it is empty on every current plan.
  3. Whitelist. If plan_employees is non-empty, keep only those people. Empty means no restriction. The AMB TT Salesman plan lists 22 people out of the 76 who hold the Pre&Vansales role.

Once a person is in scope, their transactions are their own rows plus every row belonging to anyone below them in the reports_to tree, walked to any depth. A salesman with no reports sees only himself. A supervisor's SALES_ACH therefore sums the whole team's sales against the whole team's targets. Sales office is no longer used to widen scope.

Transactions

The only input the formulas read. Everything is a row with a type, an amount and a period.

The engine filters on emp_uid and period, where period is the string YYYY-MM. Amount is in the row's currency and converted to the plan currency through exchange_rate when rates exist, otherwise taken at face value. Product and customer rows are joined so formulas can filter by brand, category, channel, group, strategic flag or tag.

KPI Library

A KPI is a named formula. Plans borrow it and add a weight, a target and a slab.

Each definition has a code, a category, a unit, a direction and a formula in JSON. The formula is what the engine runs. Unit and direction are labels for the UI. There are five formula types.

simple
One aggregation over filtered rows: SUM, COUNT, COUNT_DISTINCT or AVG of amount, quantity, customer_uid or product_uid.
ratio
numerator ÷ denominator × multiplyBy. With multiplyBy 100 the output is a percentage. Denominator 0 gives 0.
growth
Current period metric versus the same month last year, or previous month with compareWith. Output is a percent change. The prior period is queried from the database, not from the in-memory rows.
team
SUM, AVG or COUNT of a metric across direct reports only. Queried per report from the database.
static
Returns defaultValue. ZERO_SALES uses this and always reads 0 until an external feed sets it.

Here is the SALES_ACH formula exactly as stored. It is the one payout KPI on every salesman plan.

{
  "type": "ratio",
  "numerator":   { "aggregation": "SUM", "field": "amount", "transactionTypes": ["sale", "return"] },
  "denominator": { "aggregation": "SUM", "field": "amount", "transactionType": "target" },
  "multiplyBy": 100
}
// numerator with both sale and return in the array = SUM(sale) − SUM(return)

Four behaviours to know before you check numbers by hand

  • Net sales rule. When transactionTypes contains both sale and return the engine subtracts returns. The array form does not pull in bad_return.
  • Return superset. A single transactionType: "return" matches both return and bad_return. That is why the BAD_RETURN denominator equals return + bad_return.
  • Per-day KPIs. SERVICE_LEVEL, JP_ADHERENCE, JP_COVERAGE and PRODUCTIVITY are evaluated one day at a time and the daily numerators and denominators are summed before dividing. A customer visited on four days counts four times. Do not expect these to match a month-wide COUNT DISTINCT.
  • Target is informational. The plan's target_value is stored on the result but the number the slab sees is the raw formula output. A ratio KPI must therefore already be a percentage of target, which is why SALES_ACH divides by the target transaction rather than the plan target.

Creating a KPI validates only that the JSON parses and the type is one of the five. It does not check that the transaction types exist in the data, so a formula can be valid and still return 0 forever. Deleting a KPI only sets is_active = false; plans that reference it keep working.

Plan anatomy

Fifteen tables hang off one plan row. The builder shows about half of them.

The header row holds name, status, plan_type, effective dates, base_payout and currency_uid. Currency is mandatory. Status must be active for the plan to appear on Run payout and Simulate, and for the nightly cron to pick it up. Base payout is the amount a percentage slab rate is applied to. Every current plan has it at 0 because they all use per_achievement_point rates.

Slab tiers, and how a rate becomes money

A slab set belongs to one KPI, optionally to one role. The engine picks the set named on the plan KPI, else the set matching the employee's role, else the set with no role. With no set at all it uses a linear fallback of 5 percent of base payout at full achievement, which is 0 on every current plan.

rate_typeRaw payout formulaNeeds base_payout?
per_achievement_point(achievement − tier min) × rateNo
percentagebase_payout × rate ÷ 100Yes
fixedrateNo
per_unitactual value × rateNo

Then weighted = raw × weight ÷ 100, and gross is the sum of weighted across payout KPIs. Tier boundaries honour the min and max inclusive flags, so a tier written as min 95 exclusive, max 105 inclusive catches 96.68 and 105.00 but not 95.00. An achievement below the first tier gets rate 0.

Deduction bands

For each monitor KPI the engine tests every active band whose role matches. Among the bands the value falls in, the one with the largest deduction wins for that KPI. The winning percentages are added across KPIs, capped at 100, and that share of gross is removed. Bands compare against the raw formula output, so for a ratio KPI they must be written in percent.

Reject from any stage sets rejected with a comment. Every action appends an approval_log row, which you can see under approval_history on the payout endpoint. A rejected payout is not pending, so a re-run does not replace it. Delete it through the database if you need the engine to regenerate it.

History

The audit trail is separate from approval_log. It records plan created and updated with the changed fields, every engine run as refreshed or submitted with total and count, and the day-one batch promotion. Filter the History page by entity type: plan, calculation-run, payout-batch. Sub-section saves such as KPI weights or slab edits are not audited, so compare the plan JSON before and after if you need proof of a change.

Create a plan

A test plan for Pre&Vansales salesmen that you can run against the May data without touching the real ones.

The goal is a plan whose result you can predict. Use two people, one payout KPI, one monitor KPI. Employee 5897 lands in slab tier 2 with a deduction, employee 8938 lands in tier 2 above 100 percent with none. You already know their answers: 470.40 and 2,761.50.

1Create the header

Plans → New Plan. Name it TEST TT Salesman, type monthly, dates 2026-01-01 to 2026-12-31, currency SAR, base payout 0. Submit opens the builder.

  "name": "TEST TT Salesman", "plan_type": "monthly",
  "effective_from": "2026-01-01", "effective_to": "2026-12-31",

Verification checklist

  • employee_count on the run equals your whitelist, or the role headcount if no whitelist
  • linear on a weighted KPI means no slab set was found and the payout is 0
  • remember net sales subtracts return only, and a single "return" type includes bad_return
  • find someone at exactly 95.00 or 105.00 and confirm which tier they land in
  • percent KPIs need percent bands; 0.4 to 0.5 never matches 45.96
  • the builder shows the total in the header of KPI's & Weights
  • Home total for the period is the sum of all non-simulation runs, so re-runs do not double count
  • closed month → submitted; current month → pending until the last day

Known data issues

Found while verifying the May run. None are engine bugs; all are configuration or data.

BAD_RETURN bands are in the wrong unit

The AMB TT plan's bands are 0.4 to 0.5 and 0.5 to 0.6 but the formula outputs a percentage. Employee 8938 has 100 percent bad returns and 5897 has 45.96 percent, and neither was deducted. The bands almost certainly mean 40 to 50 and 50 to 60. Check the other eight salesman plans for the same pattern.

OVERDUE and DISTRIBUTION always read 0

There are no overdue or ir_audit rows in the May data. OVERDUE band 1 at 2 to 5 percent can never fire. DISTRIBUTION's bands are inactive so it is harmless for now.

ASM plans have no roles

AMB - ASM and FRZ - ASM will always produce zero employees until a role is ticked on the Plan tab.

Base payout is 0 everywhere

Fine for per-point slabs, but any tier switched to percentage rate will pay 0 until base_payout is set.

Sql/schema.sql is stale

The file in the repo describes the old id-keyed schema. The database in use is uid-keyed. Use the SELECT statements in the controllers as the column reference, not that file.
